### Concurrency risks the implementation MUST address (from the architecture investigation)

- **CR-2 Stale-history capture:** the worker runs against a frozen post-context-build snapshot; capture a history-length/version fence at spawn and RE-VALIDATE before `process_ai_response`; on mismatch (effects lifecycle at main.py:6743, transition repair, or a player turn advanced history), DISCARD the welcome. - **CR-3 Save/Load/Reset supersession wiring:** restore/reset handlers must supersede + `quiescent.wait()` the welcome scope before mutating, so no unreaped child and no `os._exit` racing an in-flight write.

## PANEL ROUND 2 (B-architecture) — findings folded (2026-08-25)

The blind panel proved the option-B off-thread design is architecturally sound and lean (single owner-mandated worker, one cancellation mechanism reusing the existing `LiveTurnScope` supersession, no new store/persisted format, dead synchronous path swept), and confirmed `game_started` retiming, the `scope=` param, and #210 resume-note inclusion are backward-compatible. It also found the following SPEC gaps — all closable within option B with no new mechanism except the status channel (D-214-4). These corrections SUPERSEDE the corresponding Task 2/3 steps.

**CR-1 supersession must fire at the SocketIO ENQUEUE boundary, not a game-thread line.** Player input and Save/Load/Reset arrive on SocketIO handler threads (`handle_user_input` web/web_interface.py:2564; `handle_action` :2578), NOT the game thread — the game thread only sees input by blocking in `WebInput.readline()` -> `user_input_queue.get()` at main.py:6808. So: `handle_user_input` must call `welcome_scope.request_supersession("player_acted")` BEFORE `user_input_queue.put(...)` (mirroring how `handle_action` supersedes the live scope), and the game thread, on waking from input, must treat a superseded welcome slot as DISCARD-ONLY before processing the input. The prior "supersede at 6808 / drain at 6704" ordering is unimplementable (both points are game-thread-local; the race is cross-thread at the queue).

**CR-2 fence must be captured over the EXACT frozen request object and cover the first-iteration mutation.** The version/length+content fence is captured over the same message list the worker was handed (post-context-build, post-`order_conversation_messages`, at the main.py:6682 save point), and revalidated on the game thread immediately before `process_ai_response`. It must account for the unconditional first-iteration `truncate_dm_notes`+`remove_duplicate_messages` at main.py:6706-6707 (either fence AFTER 6707, or compute the fence over the frozen request messages, not the pre-truncate history) — else a valid welcome is spuriously discarded (false-negative recreates "durable prompt, no welcome").

**CR-3 quiescence + Save/Load/Reset wiring (the deepest fix — 4 reviewers converged).** (a) The welcome worker uses its OWN `LiveTurnScope()` (not the global `_active_scope`, per L2), so the existing `close_live_turn_scope` NEVER sets that scope's `quiescent` (it only acts on `_active_scope`, live_provider_call.py:154/158). Therefore the WORKER must set `welcome_scope.quiescent` itself in a `finally` on ALL exit paths (success, supersession, error) — otherwise `quiescent.wait()` blocks the game thread FOREVER (a freeze). (b) Collapse the redundant `done` Event into the scope's existing `quiescent` Event + a nullable result slot: worker-terminated + slot-populated-and-not-cancelled -> hand back; else discard. One Event, not two. (c) Save/Load/Reset must resolve an effective scope = `get_live_turn_scope() or get_active_welcome_scope()` at THREE decision points — the gate (web/web_interface.py:2592) AND the restore-handler body (:2664) AND the reset-handler body (:2709), all of which currently branch on `live_scope is not None` and would otherwise SKIP supersession for the welcome scope (falling straight to `os._exit(0)` racing an in-flight welcome write). (d) The hand-back torn-write window: the welcome scope's `quiescent` must be set only AFTER the game-thread hand-back (`process_ai_response` or discard) COMPLETES, and restore/reset must `quiescent.wait()` on THAT — so a Load cannot land between "worker thread exited" and "welcome applied to disk." (e) `get_active_welcome_scope()` is a thin accessor mirroring `get_live_turn_scope()` (justified: the B1 requirement that Save/Load not be refused), one caller family; not a scope registry.

**Status channel (Player-Experience F1 -> new owner decision D-214-4).** The worker's heartbeat `_emit_working` -> `status_manager.update_status(msg, True)` drives the GLOBAL `is_processing` flag; both frontends disable the command input on `status_update{is_processing:True}` (game_interface.html:5818-5831; useUiMode.ts:72 via session.ts:71). So within one heartbeat cycle the welcome RE-LOCKS the input that Task 2.3 just unlocked — defeating "interactive during the welcome." Also makes the Save/Load `is_processing()` gate term racy (must gate on scope presence only during the welcome window). FIX REQUIRES a non-input-blocking welcome-pending status channel (see D-214-4) — the background welcome's liveness must show honest motion ("The DM is recalling your journey…") WITHOUT setting the input-locking `is_processing=True`. This is a frontend change + a status-semantics decision, escalated as D-214-4.

**Acknowledgment (Player-Experience F2).** When input is enabled before the welcome exists, show an honest non-blocking pending affordance ("The DM is recalling your journey — start typing anytime, or wait for your welcome back"); and if the player acts first and the welcome is cancelled, surface a one-line honest notice ("Welcome-back skipped — you jumped right in"). Never silent (a silent no-welcome is indistinguishable from the OBSERVED failure this plan calls a FAIL). #116/#210 hydration (recent history + location widget) is disk-backed and welcome-independent — assert that invariant so it never regresses behind the cancellable worker.

**Policy + worker lifecycle (Concurrency F4).** The worker must pass `policy="required"` for T067 (in `_REQUIRED_TASK_IDS`) — else `call_live_provider` raises `LiveProviderUnavailable` on the FIRST transport blip instead of reissuing (welcome abandoned-to-error). The worker thread must be non-daemon and reaped on shutdown (or shutdown supersedes+reaps it) so a dying game thread cannot orphan an unbounded-reissue child burning tokens.
