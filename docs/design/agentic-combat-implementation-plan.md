# Agentic Combat Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` only after the owner approves this reviewed plan. Each numbered slice is implemented and accepted independently. Read issue #193 live before every session. The `superpowers:*` skills are process tooling only and carry no doctrinal authority: on any conflict between a skill instruction and issue #193, #193 wins and the conflict is reported.

**Goal:** Deliver the approved v8 agentic-combat design as eight narrow, playable vertical slices plus one final cumulative release gate while preserving the proven turn-based experience, existing saves, and the current crash-convergent mechanics substrate.

**Architecture:** Existing encounter JSON and `combatState` remain the combat coordinator. Models author disclosure-safe semantic proposals; code reconciles canonical identity and represented rules, atomically claims accepted transitions, stages minimal value-level mutations, applies mechanics, and publishes committed facts. Work is mapped horizontally by lane but implemented vertically by real gameplay scenario; no new combat store, WAL, workflow framework, hash authority, hidden rollout switch, or comprehensive rules engine is introduced. This plan is COMBAT-ONLY: save/load/reset crash-convergence (#201), companion-memory persistence (#200), busy-lock/D-6 debt (#202), terminal out-of-turn input (#203), and build/startup liveness + cross-process build cancellation (#204) are spun out.

**Tech Stack:** Python 3.9+, JSON campaign files, existing OpenAI-compatible provider router, Gemma through LM Studio, native Windows Git/process semantics, unmodified NDJSON headless client, live browser/Playwright acceptance.

## Global constraints

- Canonical doctrine is live GitHub issue #193. Dynamically record its version and `updatedAt` at session start, before reviewed-plan execution, and before push/merge decisions.
- Compatibility authority is the current `origin/main` ancestry only. The NPC personality/voice lineage in this branch is a prototype and must be revalidated before use.
- This plan is FULL tier and **COMBAT-ONLY**: only combat, combat prompts, the combat/encounter schema, combat persistence plus combat's own Load/Reset-supersession fencing, providers as used by combat, and combat player-visible behavior are touched. Out-of-combat work found during the 2026-08-23 narrowing is spun out to independent issues and is NOT part of this plan: **#200** companion-memory persistence, **#201** crash-safe Save/Load/Reset convergence, **#202** busy-lock/D-6 debt, **#203** terminal out-of-turn input owner, **#204** build/startup provider liveness + cross-process module-build cancellation (under #186).
- Persisted play-path schemas are frozen until the owner approves every additive field in the field-level gate below.
- Deterministic tests are local and untracked. They may prove parsing, arithmetic, serialization, and I/O only; they never simulate player-facing content.
- Player-facing acceptance uses real OpenAI and Gemma calls through the unmodified native-Windows game. Do not use Qwen unless the owner explicitly requests it.
- Quick Roll remains display-only. The player submits every player-owned roll through normal input.
- Provider calls and human waits occur outside filesystem locks. Busy waits or queues; busy never becomes refusal.
- No fixed gameplay deadline, token cap, abandoned provider work, code-selected tactic, `Defend` fallback, prose/regex/type/faction semantic authority, or silent provider bypass.
- Two-strikes doctrine is mandatory: after two failed fixes for the same player-visible symptom, stop implementation; reproduce from a fresh `origin/main` baseline, identify the causal mainline change, and bisect one layer below the repeated patch surface before proposing another fix. The owner reviews that evidence before work resumes.
- Existing encounters with legacy provenance remain legacy automatically. Slice 1 removes the hidden/default-off selector and makes every genuinely new encounter use the typed agentic path on the unmerged implementation branch; the branch cannot merge or deploy until the final cumulative gate passes.
- Do not change unrelated travel, module generation/build, startup, save/restore/reset internals, companion-memory persistence, non-combat locks, or general UI behavior. Combat interacts with the shared party-transition/campaign locks only as needed for its own atomicity and for Load/Reset to supersede in-flight combat writes.
- Do not commit `.superpowers/**`, local tests, captures, runtime files, secrets, or model artifacts. Never use `git add -A`.
- Implementation never starts in this design worktree. It starts from a clean worktree whose initial production diff against live `origin/main` is empty; the approved design and converged plan are the only documentation imported before code.
- **No P2c dependency.** This combat-only plan builds and publishes no modules and never touches the module-lifecycle store, so it has no dependency on the P2c store-removal cleanup. (The P2c linkage existed only through the now-spun-out build/save/lock work; see #201/#202/#204.)
- All new Python/console/protocol/player-facing strings are ASCII-only (Windows cp1252 hard platform fact); no em dashes, smart quotes, or emoji in any new output surface, including recovery/wait/progress status text.
- Any new SRD-derived rules/content (reaction, spell, multiattack contracts) carries the repository's `_srd_attribution` line ("Portions derived from SRD 5.2.1, CC BY 4.0").

## Dynamic execution pin

At the start of every implementation session, record—not embed as authority—the outputs of:

```powershell
git branch --show-current
git rev-parse HEAD
git rev-parse origin/main
git merge-base --is-ancestor origin/main HEAD
git status --short
```

Stop on ancestry mismatch, tracked line-ending churn, a policy-epoch change, or an unexpected mutable game process holding campaign files. Before trusting any lock- or timing-sensitive acceptance result, run the issue #193 Part 4 orphan-process sweep (enumerate and terminate stray game/provider/build processes from earlier runs) and record the sweep in that probe's evidence manifest.

The implementation-base gate is stricter than ancestry: before the first production edit, `git diff --exit-code origin/main...HEAD -- '*.py' '*.json' '*.txt' '*.html' '*.tsx'` must pass. The current design branch intentionally contains non-main NPC prototype work and therefore can never satisfy this execution gate. Prototype files are imported later only as individually reviewed patches; their branch lineage is never merged wholesale.

## Mandatory lock order

Every combat entrant uses one acyclic order (Load/Reset appear only insofar as they supersede in-flight combat). A path skips locks it does not need but never acquires them in another order:

```text
party-transition authority
  -> active encounter .combat.lock
  -> module-refresh authority
  -> campaign-mutation authority
  -> sorted canonical character/file mutation leases
```

The campaign authority never wraps a later acquisition of `.combat.lock`. The combat slices route combat claim/freeze and combat mutations through this order; Load/Reset supersede in-flight combat before mutating. Provider calls and player waits hold none of these locks.
