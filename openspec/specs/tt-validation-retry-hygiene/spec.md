## Purpose

Prevent retry-correction contamination of persistent conversation history while preserving deterministic, bounded validation retry behavior.
## Requirements
### Requirement: Correction instructions SHALL remain transient

Validation correction instructions SHALL NOT be persisted as user turns in canonical conversation history.

#### Scenario: Fail then clean retry
- **WHEN** attempt 1 fails and emits correction instruction
- **AND** attempt 2 succeeds
- **THEN** correction context SHALL be transient retry input only
- **AND** persisted conversation history SHALL contain zero correction user turns

### Requirement: Correction metadata SHALL be validation-local

Correction data SHALL be held in validation-local state and discarded when retry flow ends.

#### Scenario: Metadata isolation
- **WHEN** correction instruction is generated
- **THEN** it SHALL be stored outside `conversation_history.json`

#### Scenario: Metadata lifetime
- **WHEN** validation succeeds or retries exhaust
- **THEN** correction metadata SHALL be discarded

### Requirement: Retry correction context SHALL be bounded

Retry correction text SHALL not be generated for failures whose only invalidation source is an already-reconciled authoritative domain.

#### Scenario: Reconciled travel-only complaint produces no retry correction
- **GIVEN** deterministic runtime already reconciled travel state sync successfully
- **AND** the LLM validator complains only about travel action plumbing
- **WHEN** retry handling evaluates the failure
- **THEN** runtime SHALL suppress that complaint
- **AND** SHALL NOT generate retry correction text for that domain

#### Scenario: Reconciled NPC-only complaint produces no retry correction
- **GIVEN** deterministic runtime already reconciled NPC scene presence successfully
- **AND** the LLM validator complains only about NPC arrival movement plumbing
- **WHEN** retry handling evaluates the failure
- **THEN** runtime SHALL suppress that complaint
- **AND** SHALL NOT generate retry correction text for that domain

#### Scenario: Mixed-domain failure still generates bounded correction
- **GIVEN** an LLM failure includes both reconciled-domain complaints and unreconciled failures
- **WHEN** retry handling evaluates the result
- **THEN** correction text SHALL reference only the unreconciled failure
- **AND** SHALL exclude already-reconciled domain complaints

### Requirement: Existing retry limits SHALL remain stable

Retry loop SHALL short-circuit repeated deterministic impossible-correction cycles.

#### Scenario: Same impossible deterministic reason repeats
- **GIVEN** the same deterministic impossible-correction reason repeats across retries
- **WHEN** retry guard evaluates reason sequence
- **THEN** loop SHALL short-circuit early with deterministic system guidance

### Requirement: Correction audit trail SHALL be separate

Correction diagnostics SHALL be logged in dedicated validation/audit channels, not conversation history.

#### Scenario: Audit logging
- **WHEN** correction is generated/applied
- **THEN** audit output SHALL include timestamp, source, correction, and retry outcome
- **AND** SHALL remain separate from canonical conversation history

### Requirement: Retry Corrections SHALL Remain Transient

Correction notes generated by validation retries SHALL remain transient and SHALL NOT persist in conversation history.

#### Scenario: Fail then clean retry
- **WHEN** attempt 1 fails validation and emits a correction note
- **AND** attempt 2 succeeds after correction
- **THEN** correction context SHALL be passed only as transient retry input
- **AND** conversation history SHALL contain zero persisted correction user turns

#### Scenario: Retry exhaustion
- **WHEN** retries exhaust after repeated failures
- **THEN** transient correction notes SHALL not be written into persistent history
- **AND** system error handling SHALL remain fail-closed

### Requirement: Retry Path SHALL Be Covered by End-to-End Regression

The validation retry flow SHALL have one integration-style regression that exercises deterministic failure, transient correction injection, and clean retry success.

#### Scenario: Integration regression path
- **WHEN** the regression test runs against retry flow
- **THEN** deterministic failure SHALL produce transient correction input
- **AND** subsequent clean response SHALL pass without history pollution

### Requirement: Retry exhaustion SHALL emit player-visible fail-closed guidance

When validation retries exhaust, runtime SHALL emit an immediate player-visible system message while preserving fail-closed control flow.

#### Scenario: Retry exhaustion on live narrator turn
- **WHEN** the validation loop exhausts retries for a live narrator turn
- **THEN** the runtime SHALL emit a visible `[SYSTEM]` message to the active user interface in the same turn path
- **AND** the runtime SHALL remain fail-closed for the rejected turn

### Requirement: Player-facing retry exhaustion guidance SHALL remain non-technical

The player-facing retry exhaustion message SHALL provide actionable retry guidance without exposing detailed validator jargon.

#### Scenario: Deterministic validation reason exists during retry exhaustion
- **WHEN** the runtime has a detailed deterministic or validator rejection reason
- **THEN** the player-facing system message SHALL use concise non-technical guidance
- **AND** the detailed reason SHALL remain available in debug logging rather than the main play surface
